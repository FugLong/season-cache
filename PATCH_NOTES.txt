v1.3.0
-----------------
Fast section-scan reconciler, authoritative coverage-driven snow removal, player-relative LOD coverage.

Core reconciler rewrite (ChunkSeasonReconciler):
  Previous design queried Serene Seasons temperature per column (up to 256 queries per
  chunk) and cross-referenced heightmap, sky visibility, biome, and column classification
  on every reconcile pass. The new design uses the coarse chunk-level coverage boolean
  (the same signal that drives the LOD shader) as the sole decision input, then scans
  chunk sections via ChunkSection.hasAny() palette checks to locate snow and ice blocks
  without iterating sections that contain neither. Only sections with target blocks are
  iterated — far cheaper than the previous per-column world-query approach.

  A neighbour gate cross-checks the four cardinal loaded neighbours before acting on a
  coverage value that would change the chunk's state. If loaded neighbours clearly agree
  with coverage, the decision is accepted. If neighbours are inconclusive or absent, a
  four-point multi-sample fallback fires (quadrant positions to avoid structure heightmap
  bias at the center point), using the same SS temperature oracle as the coverage builder.
  This protects against incorrect coverage center-samples caused by village structures
  and other terrain modifications.

Season transition removal path (ChunkSeasonQueue, SeasonCacheMod, ChunkSeasonStore):
  On epoch change the previous design re-enqueued all loaded chunks through the normal
  reconcile path, which had to wait for coverage re-derivation before it could make
  removal decisions. The new design captures the full set of snowy chunks from the
  outgoing epoch before the transition fires, sweeping both in-memory regions and sidecar
  files on disk so distant regions outside render distance are included. This snapshot is
  stored in a plain Set<ChunkPos> independent of the store, immune to epoch eviction and
  coverage re-derive overwrites. Loaded chunks from the snapshot are enqueued sorted by
  Chebyshev distance from the player, inserted at the front of the reconcile queue, and
  bypass the proximity gate so they clear as fast as the budget allows. Chunks that were
  unloaded at transition time are caught by onChunkLoad when they next load via the same
  snapshot set.

  reconcileRemoveOnly uses multiPointSample to verify whether the chunk should remain
  snowy in the new season before removing blocks, correctly preserving snow in cold biomes
  (snowy_taiga, snowy_plains, etc.) that stay below the temperature threshold across the
  transition.

LOD shader delta fix (SeasonCacheMod):
  onChunkCoverageComputed now checks isChunkClean before sending a delta to clients. If
  the reconciler has already run on a chunk and confirmed its state, the coverage re-derive
  no longer overrides it with a potentially stale value. This eliminates LOD shader
  decoupling where the shader showed snow that no longer existed on the ground.

Config defaults changed:
  cleanupMode: CONSERVATIVE -> AGGRESSIVE
  gameplayBudget: MEDIUM -> HIGH

Stale code removed:
  seasonalColdOverrides field and setSeasonalColdOverrides in ChunkSeasonReconciler — the
  new reconciler does not perform per-column biome classification and no longer needs the
  override set. The coverage builder still uses it for its own temperature sampling.

Season Cache — Development History
===================================

v1.2.0
-----------------
IO-thread heightmap reading: multi-hour initial build → tens of seconds.

Problem addressed:
  UnloadedChunkCoverageBuilder called ChunkGenerator.getHeightOnGround() on the
  server tick thread for every unloaded chunk. For the noise-based overworld
  generator this runs the full noise stack and takes 5-10 ms per call. With
  100 K+ unloaded chunks the initial coverage build at server start took several
  hours, blocking accurate snow display for the entire map during that window.

Root cause:
  The CompletionService worker pool offloaded only the trivial
  provider.shouldSampleSnowCoverage() call (a single boolean field read — literally
  "return sample.snowy()"). All expensive work — getHeightOnGround, biome lookup,
  SS query — remained on the tick thread.

Fix — RegionHeightmapReader (new class):
  Reads stored MOTION_BLOCKING_NO_LEAVES heightmaps directly from Anvil .mca files
  without invoking the chunk generator. The entire region file is read in one
  syscall (Files.readAllBytes), then per chunk:
    1. Decompress with GZip (type 1) / Zlib (type 2) / raw (type 3).
    2. Parse the NBT byte stream with a lightweight targeted parser that stops
       reading as soon as the "Heightmaps" compound is found — never touches
       the large "sections" block-data list in practice.
    3. Decode the SimpleBitStorage packed long array (9-bit entries for the
       overworld, no word-spanning in Minecraft 1.18+):
         bitsPerEntry  = 32 - Integer.numberOfLeadingZeros(worldHeight)  [= 9]
         valuesPerLong = 64 / bitsPerEntry                               [= 7]
         stored[i]     = (longs[i/7] >> ((i%7)*9)) & 511
         surfaceY      = stored[centerIndex] + bottomY - 1
    4. Returns UNAVAILABLE sentinel for corrupt/old-format chunks; the caller
       falls back to the generator only in that case (rare for 1.21.1 terrain).

  Results reflect actual player-modified terrain rather than generator-only
  heights, which is also more correct for modified worlds.

Fix — UnloadedChunkCoverageBuilder (major refactor):
  Removed: workerPool, CompletionService, currentRegionFile/Header/HeaderIndex,
           inflightChunks, inflightTasks, readHeader().
  Added:
    - ConcurrentLinkedQueue<List<ChunkSurfaceEntry>> completedBatches —
      IO thread posts completed region batches; tick thread drains them.
    - AtomicInteger inflightRegions — tracks outstanding IO tasks. Tasks always
      offer() to completedBatches BEFORE decrementing, guaranteeing the
      completion check (pending empty AND inflight == 0 AND queue empty) is
      race-free.
    - volatile boolean shutdownRequested — set by shutdown(); pending IO tasks
      skip the file read and post an empty batch immediately, so the IO thread's
      shutdown drain completes in microseconds at server stop.
    - currentBatch / currentBatchIndex — spreads large region batches (up to
      1024 chunks) across multiple ticks to bound per-tick cost.
  The tick thread now does only getGeneratorStoredBiome + snapshotCoverageSample
  per chunk (both sub-millisecond), with no noise computation.

Fix — RegionIOThread:
  Added submitHeightmapRead(Runnable) at MEDIUM priority. Heightmap reads run
  ahead of LOW-priority writes/invalidation walks but do not preempt HIGH-priority
  loads blocking active reconciliation. At startup with no players nothing competes
  at HIGH, so reads proceed at full IO-thread throughput.

Fix — PRECACHE budget profile (RuntimeTypes + SeasonCacheConfig):
  New BudgetProfile.PRECACHE with defaults:
    precacheChunksPerTick    = 16
    precacheMaxMillisPerTick = 20 ms
    precacheRegionsPerTick   = 64
  Used automatically for the initial server-start coverage build (SERVER_STARTED).
  Season-change rebuilds still use gameplayBudget.

Minor — compact JSON sidecar files (ChunkSeasonStore):
  Removed setPrettyPrinting() from the GSON instance. Sidecar JSON files are now
  written compact (no whitespace), reducing file size and write time.

Expected build time after fix:
  IO thread: ~50-150 ms per region (read + decompress 1024 chunks + NBT parse).
  300 regions × 100 ms = ~30 s; 1000 regions × 100 ms = ~100 s.
  Tick thread: biome + SS query at ~0.05-0.1 ms/chunk — not the bottleneck.
  Overall: hours → 30-120 seconds for typical explored worlds.


v1.1.0
-----------------
Hysteresis band: smooth season transition thresholds.

Problem addressed:
  The hard binary cut at 0.15f against getBiomeTemperature() painted a visible contour
  line through the spatially continuous temperature field produced by the combination of
  SS's seasonal modifier, vanilla elevation-based temperature decay, and biome boundary
  blending. This produced strips of chunks in conflicting snow/ice states during season
  transitions.

Core change — continuous coverage ramp (SereneAwareSeasonProvider):
  The binary threshold comparison is replaced with a ramp + deterministic noise model.
  A new config field hysteresisBandWidth (default 0.06f) controls the half-width of the
  ambiguous zone around the 0.15f threshold:

    margin = 0.15 - adjustedTemp    (positive = colder than threshold)
    coverage = clamp(margin / bandWidth * 0.5 + 0.5, 0.0, 1.0)

  Outside the band the mod is fully authoritative (coverage == 0 or 1, no hash).
  Inside the band coverage is resolved per-column by a deterministic noise function:

    shouldSnow/Ice = columnNoise(worldX, worldZ, epoch, worldSeed) < coverage

  The noise is seeded on absolute world coordinates (not chunk-relative, avoiding a
  16-block grid artefact at chunk boundaries), plus the epoch (pattern rotates at season
  change, stable within an epoch). Uses SplitMix64 finalisation for fast, well-distributed
  output. The cached climate bits remain a single bit per column — no schema change.

Ice — shoreline-seeded creation (ChunkSeasonReconciler):
  Aggressive-mode ice creation is now restricted to cells horizontally adjacent to solid
  land at water-surface Y (cardinal neighbours only). The mod seeds the freeze at the
  shoreline; the random tick system propagates it inward naturally. This eliminates
  checkerboard ice patterns on open water and matches the real-world behaviour of a
  freeze front advancing from shore. Ice removal remains unrestricted.
  
  Neighbour lookups in unloaded chunks return AIR, which fails the solid-land test —
  conservative by default (no spurious freezing at chunk load boundaries).
  Ice blocks (all three variants) are explicitly excluded from the solid-land test so an
  existing ice sheet does not seed further freeze propagation through the mod.

Bug fix — already-loaded chunks not reconciled on season change (SeasonCacheMod):
  onSeasonChanged cleared the reconcile queue but did not re-enqueue chunks that were
  already loaded at the time of the transition. Those chunks would not re-fire
  ServerChunkEvents.CHUNK_LOAD, so they retained stale snow/ice indefinitely until
  unloaded and reloaded by natural player movement. This produced a checkerboard
  pattern of reconciled and unreconciled chunks across the loaded area.

  Fix: SeasonCacheMod now maintains a loadedChunkKeys map (dimension → Set<Long>)
  populated by onChunkLoad and pruned by a newly registered onChunkUnload handler.
  onSeasonChanged iterates this map after clearing the queue and re-enqueues every
  tracked chunk that isChunkClean returns false for, with the requeue count logged.
  Fully-clean regions still short-circuit normally.

  hysteresisBandWidth (float, default 0.06):
    Half-width of the hysteresis zone around the 0.15f threshold. Changing this value
    is included in epochConfigHash(), triggering a full re-reconcile across all chunks.
    Tuning: 0.04 (narrow/subtle), 0.06 (default), 0.10 (wide/soft transition).

Feature — proximity-gated queue processing (ChunkSeasonQueue, SeasonCacheConfig):
  The reconcile queue now deprioritises chunks that are far from any online player
  rather than processing all chunks strictly FIFO. When proximityGateChunks > 0
  (default 8), a chunk dequeued for processing is deferred to the back of the queue
  if no online player is within that many chunks (Chebyshev distance) of it.

  Starvation guard: a chunk that has been waiting longer than maxChunkDeferMs
  (default 30 000 ms) is processed unconditionally regardless of proximity, ensuring
  every queued chunk is eventually handled.

  Deferral cap: at most chunksPerTick * 8 proximity checks are performed per tick.
  Once exhausted, remaining chunks are processed regardless of proximity, preventing
  the tick from spinning through a large all-distant queue.

  The timestamp recorded when a chunk is enqueued is preserved when the chunk is
  deferred and re-added to the back of the queue, so the starvation timer correctly
  reflects total time in queue rather than time since last deferral.

  New config fields (neither included in epochConfigHash):
    proximityGateChunks (int, default 8): Chebyshev chunk radius. Set to 0 to
      revert to pure FIFO behaviour.
    maxChunkDeferMs (long, default 30000): starvation cap in milliseconds.


  In non-winter seasons, biomes with base temperature >= 0.15 (plains, forest, most
  temperate terrain) were still calling SeasonHooks.getBiomeTemperature per column,
  making non-winter cold-cache reconciliation as expensive as winter. Since these
  biomes are unambiguously too warm to snow or ice outside winter, they now short-
  circuit to false immediately with no SS call. This makes non-winter queue drain
  fast enough that snow and ice removal completes before the player notices.

  Biomes with base temp < 0.15 (snowy_taiga, snowy_plains, snowy_beach, etc.) still
  call getBiomeTemperature in non-winter so SS can return their seasonally-adjusted
  value — SS warms these in summer (→ false, snow removed) but may keep them cold
  in shoulder seasons (→ true based on ramp). isSnowSeason is restored as a parameter
  to shouldHaveSnowNow and shouldHaveIceNow in SeasonProvider,
  SereneAwareSeasonProvider, and ChunkSeasonReconciler.


  SeasonEpochService.SCHEMA_VERSION bumped from 1 to 2. This integer is included in
  the epoch hash, so changing it globally invalidates all stored climate bits without
  requiring a manual /seasoncache invalidate. Any future logic change that affects
  what shouldHaveSnowNow or shouldHaveIceNow return for the same inputs must also
  bump this value. The history of changes per version is documented in the constant's
  Javadoc.


  Biome lookup, classifyColumn, and shouldHaveSnowNow were all called with abovePos
  (surfaceTop + 1) — the air block above the surface. SS's weather tick evaluates
  temperature at the top motion-blocking block itself (surfacePos), not the air above
  it. The one-block Y offset caused a systematic temperature discrepancy: our reconciler
  decided a column was cold enough to place snow, but SS's tick then evaluated the
  surface block, got a slightly warmer reading, and immediately ticked the snow away.

  Fix: biome sampling (world.getBiome), classifyColumn, and shouldHaveSnowNow now all
  use surfacePos. shouldHaveIceNow was already correct. Sky-visibility is still checked
  at abovePos (the air block) since that is the semantically correct location for that
  check. Block placement and removal positions are unchanged.


  shouldHaveSnowNow and shouldHaveIceNow used a fast path in non-winter seasons that
  returned biome.getTemperature() < 0.15 directly. For seasonal override biomes
  (e.g. snowy_plains, snowy_taiga, snowy_beach) this returned true even in summer,
  because their base temperature is genuinely cold. SS warms these biomes seasonally —
  which is precisely why they are in the override set — but the short-circuit never
  asked SS for the adjusted temperature, causing snow to be incorrectly retained.

  Fix: the short-circuit is removed entirely. getBiomeTemperature is now called in
  all seasons. SS returns warm adjusted temperatures for override biomes in summer,
  the ramp gives zero coverage, and snow is correctly removed. Biomes the mod should
  never touch (PERENNIAL_COLD with neverTouchPerennialColumns=true) are already
  excluded upstream in classifyColumn before shouldHaveSnowNow is reached, so the
  short-circuit was never needed for that case.

  isSnowSeason is removed from the shouldHaveSnowNow and shouldHaveIceNow signatures
  in SeasonProvider, SereneAwareSeasonProvider, and ChunkSeasonReconciler since it is
  now unused in those methods.

v1.0.0
-----------------
Initial public release.

Serene Seasons dependency:
- SS is now a hard compile-time and runtime dependency (modCompileOnly, fabric.mod.json
  depends). All reflection removed. Direct API calls throughout: SeasonHelper,
  ISeasonState, Season.SubSeason, SeasonHooks. Place the SS jar in libs/ to build.

Core data model:
- Replaced per-column ownership bitsets with a binary cleared/not-cleared model per chunk.
- Added region-level "fully clean" promotion: when all known chunks in a 32x32 region are
  cleared for the current epoch, future loads in that region skip immediately.
- Fixed region promotion edge case: new chunks generated in a promoted region correctly
  revoke the promotion and reconcile normally rather than being silently skipped.
  knownChunkCount is incremented on revocation to keep the promotion threshold accurate.
- Added per-chunk climate decision cache (shouldSnowBits / shouldIceBits, 256 bits each).
  First reconcile of a chunk per epoch queries SS; subsequent visits use cached bits
  directly with no SS calls.
- knownChunkCount sourced from actual Anvil region headers via RegionPrecacheBuilder.

Two-tier column classification:
- Fast biome gate (tier 1) eliminates non-precipitating and perennially cold columns
  before any SS query fires.
- isSnowSeason() called once per chunk, not per column.
- Non-winter short-circuit: outside winter, tier 2 uses base temperature < 0.15f as a
  fast gate with no SS call.
- SS-derived seasonal override set: at server start, all registered biomes are scanned
  using SeasonHooks.hasPrecipitationSeasonal(). Biomes that are below the perennial-cold
  temperature threshold but seasonal by SS (e.g. Snowy Taiga) are promoted to
  SEASONAL_TEMPORARY. Built once and cached — O(1) lookup in the hot path, no per-tick
  SS cost. Automatically covers modded biomes with the same characteristics.
- Tier 2 climate decision: uses SeasonHooks.getBiomeTemperature() compared against the
  freeze threshold (0.15f) rather than canSetSnow() / canSetIce(). This is necessary
  because canSetSnow/canSetIce go through warmEnoughToRain(), which uses the rain
  threshold rather than the freeze threshold and does not push temperate biomes cold enough
  in winter. getBiomeTemperature() applies SS's seasonal modifier and matches the code path
  SS's own RandomUpdateHandler uses for weather-tick snow and ice placement. Using the
  wrong threshold caused aggressive mode to skip snow/ice placement in biomes that SS
  itself snows and freezes in winter (e.g. Plains).

Async IO (RegionIOThread):
- All sidecar disk reads and writes moved off the tick thread to a single dedicated
  background IO thread (daemon, NORM_PRIORITY - 1).
- PriorityBlockingQueue with three tiers: HIGH (blocking reconciliation), MEDIUM (adjacent
  to a player), LOW (cold loads, invalidation disk walk).
- Player neighbourhood set refreshed every 20 ticks by the tick thread. Used to promote
  nearby-but-cold region loads to MEDIUM priority.
- On cache miss, an empty placeholder is installed immediately and a load task submitted.
  The tick thread never blocks on disk. Worst case: a chunk is reconciled with a cold
  climate cache (correct but slightly redundant).
- Load deduplication: ConcurrentHashMap set prevents multiple load tasks for the same
  region from queuing simultaneously during burst loads.
- Write deduplication: pendingWritePaths set prevents redundant write tasks. Post-write
  callback re-submits if the region was dirtied while the write was in flight.
- Snapshot-before-write: data is snapshotted under the store monitor on the tick thread
  at submission time. The IO thread writes the snapshot without ever acquiring the store
  monitor, eliminating tick thread contention during writes.
- Shutdown drains remaining tasks before the thread exits so in-flight writes land.

Season-change detection:
- Replaced 200-tick periodic flush with epoch-change detection on every tick.
  Fires within 1 tick of an SS sub-season transition.
- On transition: async flush of all dirty sidecars, reconcile queue clear, log entry.
- Removed tickCounter — no longer needed.

invalidateAll:
- In-memory state cleared immediately on the tick thread (fast).
- On-disk epoch zeroing submitted as a LOW priority task to the IO thread (background).
- Progress tracked via AtomicInteger, exposed in /seasoncache status as
  "invalidation=X/Y (running/complete)".
- Command feedback updated to accurately describe the async behaviour and advise
  admins to wait for completion before restarting if full consistency is required.

Cleanup modes redefined:
- CONSERVATIVE: remove-only. Never places snow or ice. Safe default.
- AGGRESSIVE: remove and place. Corrects in both directions (spring thaw and winter onset).

Aggressive snow placement gate:
- Full-cube geometry check: prevents snow placement on fences, stairs, slabs, etc.
- seasoncache:snow_placement_blacklist block tag: excludes workstations, storage blocks,
  and similar player-crafted full-cube items. Datapack-extensible.
  Default entries in data/seasoncache/tags/blocks/snow_placement_blacklist.json.

Performance:
- setBlockState calls use NOTIFY_LISTENERS (flag 2) instead of flag 3. Clients see visual
  changes; no neighbor block update cascade fires.
- Block state reads deferred until after gate and cache checks — only paid on columns
  the mod is actually going to act on.
- belowState (snow placement surface check) only fetched inside the aggressive placement
  branch. The removal path pays nothing extra.
- PERENNIAL_COLD_THRESHOLD (0.15f) extracted as a named constant used consistently
  across classifyColumn, shouldHaveSnowNow, and shouldHaveIceNow.

Store / persistence:
- Sidecar format schema v3: dataEpoch, regionEpoch, knownChunkCount, clearedChunks
  (long[]), climateBits (ClimateEntryDisk[]).
- Dimension-safe: RegionKey and sidecar paths keyed by full dimension identifier.
  Overworld and Nether regions at the same coordinates no longer collide.
- Schema version mismatch on load: stale sidecars discarded with a log warning.
- All IO failures surfaced via LOGGER.warn / LOGGER.error.

Commands:
- status: shows provider, season, mode, queue, cleared, climateCached, cleanRegions,
  dirty, precache progress, and invalidation progress when relevant.
- invalidate all: updated feedback describes async behaviour accurately.
- mode: feedback describes what each mode actually does.
